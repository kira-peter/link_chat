# Design

## Context

见 proposal.md 的 Why。与实现相关的现状：

- `render()` 每帧固定先画 `Chrome.Frame`（标题栏与顶部分隔线）、主界面、`StatusBar`（底部分隔线与快捷键），最后才在 `renderDialog` 里把登录/注册/找回画在上面。是否「在舞台上」目前没有单独的概念，只有 `ui.Dialog ∈ {Login, Register, Recover}`。
- 主循环只有在 `needsFrames()` 为真时才挂一个 `frameInterval`（33ms）定时器，否则完全静止。所有动画共用这一个帧间隔。
- 动画时间曲线、渐变与降级已在 `pkg/tui/anim`（`EaseOutCubic`、`Depth` 的真彩/256/单色三档）。
- 登录成功统一走 `onAuthenticated`；断线重连成功也会走到这里（主界面一直可见，`ui.Dialog` 是 None）。

## Goals / Non-Goals

**Goals:**
- 「在不在舞台上」只由一个判断决定，渲染、帧调度、入场触发都读它。
- 点阵与入场都是**纯函数**：输入（尺寸、经过时间、面板矩形、能力档位）→ 单元格；可在仿真屏上逐帧断言，测试不依赖真实时间。
- 入场动画的最后一帧与「直接显示主界面」逐格一致，不留下任何残影。

**Non-Goals:**
- 不改变登录、注册、找回面板本身的内容与键位（那些在已归档的变更里定过）。
- 不做退出登录时的反向动画。
- 不为点阵做鼠标交互或视差。

## Decisions

### 1. 舞台是渲染的第一个分支

`onStage() = ui.Dialog ∈ {Login, Register, Recover} && !entrance.running`。`render()` 开头：在舞台上就只画背景与面板然后返回；否则照常画主界面。顶号提示（`DialogSessionReplaced`）不在舞台上——它需要用户看到被顶下线的主界面。用户在提示里选择重新登录后进入 `DialogLogin`，自然回到舞台。

- **替代方案：照旧先画主界面，再用背景色整屏盖掉。** 被否：多画一遍无用内容，且主界面的动画（光带等）会被 `needsFrames` 认为在运行，白白消耗帧。

### 2. 点阵：确定性的稀疏粒子，时间驱动而不是状态驱动

点阵不保存任何可变状态。给定窗口尺寸，用固定种子生成 N 个点（N ≈ 面积 / 60），每个点有起点、方向（缓慢的斜向）和速度；第 t 毫秒的位置 = 起点 + 速度 × t，对窗口取模环绕。渲染时跳过落在「面板矩形外扩一格」内的点。

- 字符按点的「深度」取 `·` 或 `.`，颜色取 `Faint`；单色下同样是这两个字符，不需要额外降级。
- 速度上限保证 100ms 内位移不超过一格（spec：相邻帧不超过一格），所以 10fps 下看起来是连续漂移。
- 关闭动画：t 固定为 0，静态点阵。
- 极小窗口：面板外扩一格后若四周都没有空间，N=0。
- **替代方案：每帧随机挪动点。** 被否：无法在测试里复现，也会闪烁。

### 3. 两档帧率：点阵单独限速

`needsFrames` 拆成「需要帧」与「最早下一帧时间」。普通动画仍是 33ms；如果当前唯一在运行的是点阵，则间隔为 100ms。主循环用 `time.After(interval)`，改动集中在 `nextFrameIn(now) (time.Duration, bool)`。

- 帧预算测试扩展：舞台静置时测得的帧率 ≤ 12fps；同时有登录按钮光带时回到普通帧率（按钮光带本来就在舞台上运行）。

### 4. 入场动画：一条时间轴、四段

入场是一个 `Entrance{start time.Time}`，进度 p = (now - start) / 600ms，用 `EaseOutCubic` 映射。四段按进度切分：

| 段 | p 区间 | 画面 |
|---|---|---|
| 压扁 | 0 – 0.25 | 面板以中线为轴高度从原值缩到 1 行；内容在高度小于面板内容所需时不再画，只画边框 |
| 拉长 | 0.25 – 0.45 | 一行亮线从面板宽度延展到整行宽度；点阵亮度同时降到 0 |
| 张开 | 0.45 – 1.0 | 亮线分为上下两条，分别从中线移向主界面顶部分隔线行与底部分隔线行；两线之间画主界面，之外画背景 |
| 结束 | ≥ 1 | 不再参与渲染，直接是主界面 |

- 「两线之间画主界面」的做法：先把主界面完整画到屏幕，然后把两线之外的行用背景覆盖，最后画两条亮线。主界面本身仍是原来的纯函数，入场只是一个遮罩层，所以「结束后逐格一致」天然成立。
- 张开阶段的终点就是 `Chrome` 的顶部分隔线行和 `StatusBar` 的底部分隔线行，从现有布局函数读，不另外写死行号。
- 亮线颜色：真彩色用 `Accent` 向白色混合的高亮；256 色与单色用粗线 `━`（不支持框线时 `=`），普通分隔线是 `─`/`-`，可以区分。
- 动画中按任意键：先 `entrance = nil`（跳到终点），再按普通流程处理该键。消息、列表更新本来就写进状态，遮罩层不影响它们。
- 时长 600ms，在 spec 的 800ms 上限之内，留出慢终端的余量。

### 5. 触发点

`onAuthenticated` 里如果「调用前在舞台上」（`ui.Dialog ∈ {Login, Register, Recover}`）且动画开启，则 `entrance.start = now`；否则不播放。断线重连时 `ui.Dialog` 是 None，所以不会播放——不需要额外的「是否重连」标记。

## Risks / Trade-offs

- **[风险] 现有端到端测试在登录后立即读屏，可能读到入场动画的中间帧。** → 测试用的 App 默认开着动画；`waitFor` 等到 `StateReady` 之后，测试辅助再推进冻结时钟或调用 `skipEntrance()`。读屏的测试统一经过已有的 `render()` 后再断言。
- **[风险] 舞台上不画状态栏，就看不到「连接中」。** → 登录面板内已有状态行（服务器地址与连接状态），这是已有行为，不受影响。
- **[取舍] 点阵在舞台上持续 10fps 刷新。** 用户选择了动态背景；通过单独限速、只在舞台上运行、关闭动画即静止来控制成本。通过 SSH 使用时用户可以关闭动画。
- **[取舍] 入场动画期间遮住了主界面的大部分，最多 0.6 秒。** 任意按键立即跳过，所以不会妨碍熟练用户。

## Migration Plan

纯客户端界面变化，无配置与协议变动，回滚客户端即可。
