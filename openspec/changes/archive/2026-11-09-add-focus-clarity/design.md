# Design

## Context

现有焦点模型是 `Focus` 枚举加一个 `Next()` 翻转（`pkg/client/state.go`）。方向键只是调用它，所以 `←` 和 `→` 做的是同一件事——这就是方向错乱的根因，不是某处写反了符号。

渲染是"状态进、单元格出"的纯函数（见 `openspec/specs/tui-design-system/spec.md`），主循环只有一个 250ms 的定时器，用于重连倒计时。没有任何逐帧动画。

约束：

- 渲染要保持纯函数：动画不能把时间藏在视图内部的可变状态里，时间要作为**参数**传入。
- 不能让静止的界面持续重绘。终端里常驻 30fps 重绘会让 SSH、慢速终端、远程桌面都不舒服。
- 要尊重现有的"动画"开关与颜色降级规则。

## Goals / Non-Goals

**Goals:**

- 方向键与屏幕空间位置一致。
- 一眼看出键盘在哪一侧。
- 空输入框有"滑动解锁"式的光带，且停止条件严格。

**Non-Goals:**

- 不做通用动画框架或时间线编排器。只有两个动画，抽象成本高于收益。
- 不做鼠标悬停高亮、点击聚焦。
- 不改变区域数量；仍是列表 + 聊天两栏。

## Decisions

### 1. 焦点用"空间位置"而不是"翻转"建模

**选择**：`Focus` 保持 `FocusList`（左）/ `FocusInput`（右），去掉对称的 `Next()`/`Prev()`，换成 `Left()` 与 `Right()`：

```
FocusList.Left()  = FocusList    // 左边界，空操作
FocusList.Right() = FocusInput
FocusInput.Left() = FocusList
FocusInput.Right()= FocusInput   // 右边界，空操作
```

`Tab` / `Shift+Tab` 仍然循环（它们本来就是"下一个/上一个"，不带方向），用单独的 `Cycle()`。

**理由**：翻转函数天然无法表达"在边界按同方向是空操作"。用位置建模后，边界行为是类型本身的性质，不需要在调用处写特例。

### 2. 光标优先于焦点移交

输入框有文字时，`←` 的含义是"光标左移"。只有当光标已经在行首时，这个键才有机会变成"去左边"。`→` 对称。

这是一个交互上的取舍：

- **选项 A（采用）**：光标在边界时再按才移交。不抢编辑键，也不要求清空。
- **选项 B**：输入框非空时方向键永远只动光标，必须用 `Tab`/`Esc` 离开。这最保守，但会让"我想回列表看一眼"变成两步操作。

选 A 的风险是：用户在行首无意多按一次 `←` 会失去焦点。缓解：移交时输入内容与光标都保留，再按 `→` 就回到原位，没有任何丢失。

### 3. 光带的数学：高斯包络

iPhone 4 的解锁光带看起来"柔"，是因为亮度沿文字呈钟形分布，而不是一个硬边亮块。对第 `i` 个字符：

```
brightness(i) = exp( -((i - center) ^ 2) / (2 * sigma^2) )
```

- `center`：光带中心的字符位置，随时间线性移动。
- `sigma`：带宽，取 2.5 个字符左右。小了像一个点，大了像整行泛白。

`center` 的运动：

```
cycle  = travel + pause
phase  = (t mod cycle)
center = -pad + (phase / travel) * (len + 2*pad)     当 phase < travel
       = (len + pad，已出界，全部熄灭)               当 phase >= travel
```

`pad` 取 `3*sigma`，让光带完全从左侧外面滑进来、从右侧外面滑出去，而不是在边缘突然出现。`pause` 是两次扫过之间的停顿，约 0.8 秒——这一点很重要，连续不断的扫动会显得焦虑，停顿才有"呼吸"。

**颜色混合**：把 `brightness` 当作 `t`，在"弱化色 → 强调色"之间线性插值。真彩色下直接插值 RGB；256 色下量化到 5 级；单色下降级（见第 5 条）。

**时间作参数**：渲染函数接收 `now` 而不是自己读时钟。这样单测可以固定 `t` 断言每个字符的颜色，也不会有"测试偶尔因为时钟而失败"。

### 4. 动画只在必要时驱动重绘

主循环现在是 `select { 事件 | 250ms 定时器 | dirty }`。改为：

- 平时仍是 250ms 定时器（重连倒计时用），空闲零额外开销。
- 有动画时，额外启动一个 **~33ms（30fps 上限）** 的定时器；动画结束或前提不成立就 `Stop()`。

"有没有动画需要跑"由一个纯函数 `needsAnimation(state, now)` 判断：

```
光带: 动画开 && 输入区拥有焦点 && 输入为空 && 无对话框
过渡: 动画开 && now < transition.endAt
```

两者都不成立时，主循环不创建高频定时器。这样静止界面没有任何持续重绘，符合规格里"静止界面不消耗刷新"。

**为什么是 30fps 而不是 60**：终端渲染每帧要输出差异字节，60fps 在 Windows Terminal 上尚可，但经 SSH 或在 VSCode 集成终端里会明显卡。光带的运动慢（一次扫过约 1.4 秒），30fps 已足够平滑。

### 5. 颜色降级用三档，不做"尽量接近"

| 终端能力 | 光带表现 |
|---|---|
| 真彩色 | 连续 RGB 插值 |
| 256 色 | 量化为 5 级 |
| 单色 / 无色 | 用 `▸` 之类的位置标记在文字下方移动，或退化为一个反色字符在文字上走过 |

单色档不尝试模拟渐变——灰度差在单色终端上不存在，勉强"插值"只会得到噪声。

### 6. 焦点过渡：标记滑动 + 缓出

焦点标记（标题行左侧的 `▌`）在两个区域标题行之间"滑动"。位置按缓出曲线（`easeOutCubic`）插值：

```
p(t) = 1 - (1 - t)^3,   t = elapsed / duration,  duration = 180ms
```

缓出的特点是起步快、收尾慢，符合"被吸过去并安定下来"的感觉。线性匀速会显得机械。

**连续切换**：如果上一个过渡没结束又切换，新过渡的起点取"当前插值位置"，而不是旧起点。这样快速来回按键不会出现先跳回去再跳走。

**实现**：焦点标记本身只占一个单元格宽，"滑动"在终端里只能是整数格。两个区域标题行的水平距离是 `sidebarWidth + gap`，约 20–30 格；在 180ms 内以整数格跳 20 多次，在 30fps 下大约是 5–6 帧——足够表现出方向与速度。

### 7. 标记不依赖颜色

焦点区域的标题前面是 `▌`（竖条），非焦点区域前面是空格。即使在单色终端、色盲用户、或者截图转灰度之后，"有没有竖条"仍然是确定的信号。颜色只做辅助强化。

### 8. 分隔线不跟随焦点

最初的设计想让分隔线靠近焦点的一侧着强调色。实现后用数据检查颜色，发现这做不到：竖线只有 1 格宽，没有"左边""右边"之分，焦点在左或在右时它是同一根线、同一个颜色。所谓"跟随"只会得到一条换了颜色的线，不传达任何信息。

所以规格改为：分隔线保持中性，焦点完全由两个标题的竖条与颜色表达。竖条（有无）与颜色（亮/灰）已经是双重信号，不需要第三个。

## Risks / Trade-offs

- **光带在慢终端上闪烁** → 帧率上限 30fps，且仅在输入区为空并有焦点时运行；用户一输入就停。设置里的动画开关作为后备出口。
- **过渡动画吃掉按键响应的感觉** → 动画期间不阻塞输入；按键立即生效，动画只是视觉跟随。
- **在行首误按 `←` 失焦** → 内容与光标都保留，`→` 即回；这是方案 A 的明确代价。
- **时间作为参数增加了调用点负担** → 只有两个视图用到，把 `now` 放进已有的 Model 结构体即可，不增加新参数。

## Open Questions

- 光带的色调是否跟随主题强调色？默认跟随（`Accent`），暗色主题下是青色，浅色主题下是深青。这不影响规格，可以在看到实际效果后再调。
