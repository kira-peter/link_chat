# Design

## Context

动机见 `proposal.md`。现状：

- 后台已有实时事件流（`admin_events.go`）：`adminEmit` 把事件按订阅者权限过滤后推给每个打开的 SSE 连接，消息事件在没有 `chat.view` 时用 `Redacted` 版本。产出点只有上线下线、注册登录、消息新增/编辑/删除、处分。
- 好友、动态、频道的请求都在 `server.go` 的请求分派里，各自有处理函数，便于在成功后补一次产出。
- 服务端日志经 `AsyncWriter` 写 stderr，同时写 `LogRing`（后台概览的最近日志）。`main.go` 负责接线。
- 服务端已依赖 tcell v2.13.10（客户端在用）和 `golang.org/x/term`。
- 后台页面是 `adminweb/` 下的纯 HTML/CSS/JS，经 `//go:embed` 打进二进制，不引外部资源。

## Goals / Non-Goals

**Goals:**
- 一份活动数据，同时驱动终端仪表盘与后台实况页。
- 终端仪表盘在交互终端里开箱即用，非交互时零影响。
- 后台实况页尽可能炫：3D、拖尾、粒子；离线可用。

**Non-Goals:**
- 当前频道上报复用心跳的可选字段，保持旧客户端可用。
- 终端仪表盘可展开系统栏与退出，管理仍在后台。
- 活动只保存在当前进程。打开终端时读取本次运行的累计数与近期活动，随后接收新活动。

## Decisions

### 1. 活动 = 扩展后台事件流，再加一个进程内订阅者

**选择**：在现有 `adminEvent` 基础上新增活动类型，复用 `adminEmit` 的分发与权限过滤。终端仪表盘作为进程内订阅者（`Server.SubscribeActivity() <-chan Activity`，有界队列，满了丢最旧的），拿到结构化的 `Activity{At, Kind, Category, Actor, Target, Channel, Summary}`，不经 JSON。新增产出点：好友申请/同意/删除/拉黑、动态发布/点赞/评论/删除、频道新建/加入，均在处理成功后调用 `s.activity(...)`；它同时喂给 SSE 与进程内订阅者。

**理由**：分发、慢订阅者处理、权限过滤都已存在且有测试；只需补产出点与一个本地出口。仪表盘不能因为慢而拖住聊天，所以和 SSE 一样是有界、丢弃式的。

**替代方案**：让仪表盘解析日志行——脆弱且拿不到接收者。

### 2. 终端仪表盘：独立包 `pkg/server/live`，tcell 绘制

**选择**：`live.Run` 接管终端。`Source` 提供初始快照与活动订阅。布局自上而下为一行统计、用户名网格和频道区、底部活动四栏。

- **启用条件**：`main.go` 用 `term.IsTerminal(stdout)` 且未指定 `-plain` 时启用；否则沿用现有日志接线。启用时，原本写 stderr 的日志处理器改为写入仪表盘的日志通道（技术日志也以「系统」类显示），`LogRing` 不变。
- **用户名网格**：按用户名稳定排列，按名字长度安排每行的位置。离线为灰色，在线按本次登录时长分四档绿色，越久越深。超出可用空间时显示「还有 N 人」。
- **频道区**：最近有消息的频道依次占一个小框（`┌ #name ┐`），最多放得下的个数；超过 8 秒无消息淡出（三档颜色后消失），腾出位置。
- **消息动画**：连线借用用户名之间的空白行与边缘，从发送者延长到接收者或频道，短暂停留后从发送者一端收回，全程约 1.1 秒。视野之外的接收者使用「还有 N 人」作为锚点。动画与消息活动的映射单独处理，便于后续为其他动作加入连线。并行上限 50 条。
- **活动四栏**：消息青、社交品红、账号绿、系统黄。每类保留本次运行的累计数与最近六次操作，按终端高度显示，最新在上。快照携带分栏数据与序列号，订阅积压时可重新对齐计数。技术日志计入终端的系统栏。系统栏预留较宽空间，长条目自动折行；按 `S` 可展开为全宽视图，再按一次返回。
- **帧率**：有动画时 30fps，无动画时只在有新活动或每秒刷新统计时重绘。
- **退出**：`q` / `Ctrl+C` 触发与 SIGINT 相同的优雅关停；`Fini` 恢复终端。

**理由**：tcell 已在依赖里、跨平台（含 Windows 控制台）；独立包便于用 SimulationScreen 测试，不碰聊天逻辑。

### 3. 后台实况页：three.js 内嵌

**选择**：`adminweb/live.html`（或主页内一个区域）+ `live.js`，three.js 固定版本（r160 的 `three.module.min.js` 与 `UnrealBloomPass` 等后期处理模块）放在 `adminweb/vendor/`，随 `//go:embed` 打包。

- **场景**：深色星空背景（缓慢旋转的星点）；在线星体发光，离线星体暗淡。频道星环按成员数相对屏幕上的最大频道缩放，并标注在线人数和成员总数。玩家星体从环外出发，客户端打开频道后飞入，切换或离开时根据新界面移动。频道消息先等玩家抵达星环，再播放流星。选中玩家时用金线连接其频道、粉线连接好友。成员名单、当前查看的频道与好友关系仅提供给持有 `chat.view` 的账号。
- **消息**：从发送者到接收者（或频道环）的贝塞尔弧线上飞行的流星，头部发光、尾部为粒子拖尾，飞行约 1.2s；抵达时粒子爆散并让目标闪一下。有 `chat.view` 时流星旁跟随一个 HTML 消息气泡（CSS2D 叠加层），抵达后淡出；否则只有流星。
- **其他活动**：上线是星体从暗到亮的脉冲；下线变暗；点赞是从点赞者飞出的心形粒子；评论是小气泡；好友同意是两颗星体之间短暂连线；处分是红色冲击波。
- **后期**：Bloom 辉光、轻微镜头缓移；`prefers-reduced-motion` 时关掉镜头运动与爆散。
- **侧栏**：实时统计（在线、今日消息、每分钟）与分类事件流（与终端日志同一套文案与类别）。
- **数据**：页面打开时请求 `/admin/api/live/snapshot`（`stats.view`），再订阅现有 SSE 事件流。

**理由**：用户选择 three.js 3D。内嵌而不走 CDN，满足后台不依赖外网、也避免第三方脚本进入管理页的安全面。

**代价**：二进制增大约 700KB（three.js 压缩版与后期模块）。

### 4. 权限与内容

- 实况快照与活动流都要 `stats.view`。
- 消息活动的完整版本（含内容、会话名）沿用 `PermChatView`，其余管理员拿到不含内容的版本：只有发送者、接收者（私聊）或频道 ID——频道名属于会话信息，同样只给 `chat.view`，没有时实况页显示为匿名频道环。
- 终端仪表盘是运维在服务器本机看到的，与普通日志同等对待：不显示消息内容与令牌。

### 5. 文案

活动简述集中在一处（`activitySummary`），终端日志与后台侧栏共用，保证两边说法一致。服务端日志目前是英文，此处用中文（与后台一致）。

## Risks / Trade-offs

- **活动量很大时动画堆积** → 终端并行连线上限 50，后台流星上限 200，超出直接丢弃最旧的，计数照常。
- **终端仪表盘吞掉了原始日志** → 技术日志仍以「系统」类出现在底部，且 `LogRing` 与后台概览不变；排障时可用 `-plain`。
- **内嵌 three.js 的维护** → 固定版本，`adminweb/vendor/VERSION` 记录来源与版本，升级时整体替换。
- **Windows 控制台的刷新闪烁** → tcell 增量刷新，已在客户端验证过可接受。

## Migration Plan

无数据迁移。已有部署若以服务方式运行（输出非终端），行为不变；在终端里直接运行的会看到仪表盘，可用 `-plain` 恢复。
