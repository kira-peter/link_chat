# Design

## Context

新工程，无既有代码或数据需要兼容。约束来自三处：

1. **技术选型参照 `claude_manager`**：Go + `tcell/v2` 的终端渲染路线已经在本机验证过中文宽度、resize 与 Windows Terminal 表现，沿用它可以少踩一遍坑；`claude_manager` 的 `pkg/views` 视图注册模式也证明了"每个界面一个 View，通过注册表挂载"的扩展方式在这个规模下是够用的。
2. **公网多用户**：服务端要面对的对手不只是网络抖动，还有凭据猜测和刷屏。
3. **存储选 JSON 文件**：这是本项目里最需要被工程化约束的一处取舍——它简单、可 diff、可人工修复，但在并发写与规模上天然受限。设计必须让这个限制**被隔离**，而不是弥漫进业务代码。

行为契约见 `specs/` 下七个能力规格；本文只解释为什么这样做。

## Goals / Non-Goals

**Goals:**

- 一套协议让服务端与客户端严格解耦：协议层不 import 任何 UI 或存储代码。
- 存储可替换：从 JSON 文件换到 SQLite 只需新增一个接口实现，业务层零改动。
- 界面质感可复用：色彩、间距、行样式、边框规则收敛到一个 `theme` 包，视图只做组合。
- 单仓库、双二进制、`go build` 即可运行，不引入代码生成步骤。
- 关键路径可测试：协议编解码、存储原子性、消息排序、折行与宽度计算都有纯函数边界。

**Non-Goals:**

- 不做多机部署的服务端集群。广播依赖进程内状态，水平扩展需要引入外部消息总线和共享存储，不在本次范围。
- 不做插件系统或主题脚本。
- 不追求 UI 框架抽象。`tcell` 之上直接写视图，不造一套通用组件框架——这个规模的界面用不上，抽象成本高于收益。
- 不做消息搜索、富文本、已读回执。

## Decisions

### 1. 用 WebSocket 承载 JSON 信封，而不是原生 TCP 或 gRPC

**选择**：`net/http` + WebSocket，每条消息一个 JSON 对象，字段为 `type` / `id` / `payload`。

**理由**：WebSocket 天然是消息边界清晰的帧，不需要自己处理粘包；同时它跑在 HTTP 之上，意味着 TLS 终止、反向代理、健康检查都能直接复用成熟方案——这对"公网多用户"是个实质性收益。JSON 让抓包和手写测试客户端变得廉价，早期调试成本远低于自定义二进制协议。

**替代方案**：
- *原生 TCP + 长度前缀*：帧开销低，但要自己实现握手、心跳、版本协商，且无法直接反代。
- *gRPC*：双向流很合适，但需要 protobuf 与代码生成，且浏览器/手工调试不友好；本项目没有多语言客户端需求，收益不足以抵消成本。
- *SSE + HTTP POST*：客户端到服务端要另开信道，连接数翻倍，不如 WebSocket 直接。

**代价**：JSON 编码开销与帧体积高于二进制。以文本聊天为负载时这个开销可以忽略（单条消息通常 <2KB），且服务端限流与帧大小上限已经封住了滥用面。

### 2. 协议层独立为 `pkg/protocol`，服务端与客户端共用同一套类型

**选择**：帧结构、错误码、请求/响应类型定义在一个包里，服务端与客户端都 import 它。

**理由**：两端共享类型意味着协议变更会在编译期暴露不兼容，而不是在联调时才发现。这是本项目唯一值得"共享代码"的地方——除此之外服务端与客户端互不引用。

**实现要点**：
- 帧的 `payload` 用 `json.RawMessage` 延迟解析，先按 `type` 分派再解码为具体结构，这样未知类型可以干净地返回 `protocol_violation` 而不是整体解析失败。
- 错误码定义为具名常量集合，并带一个 `Code` 与 HTTP 语义无关的映射表，避免错误码字符串散落在各处。
- 版本号是常量；协商逻辑放在握手处理器里，不在协议包里，保持协议包无副作用。

### 3. 服务端用"中心 Hub + 每连接两个 goroutine"的并发模型

**选择**：`Hub` goroutine 独占会话与连接映射的修改权；每条连接有读 goroutine 与写 goroutine，两者通过带缓冲的 channel 与 Hub 通信。

**理由**：这是 Go 里最容易被写对的结构。所有共享状态（在线用户、频道成员、各连接的发送队列）只在 Hub 的循环里被读写，无需锁，也就不存在锁顺序问题。写 goroutine 独占 socket 写入，避免并发写导致的 WebSocket 帧交错。

**替代方案**：
- *每会话一把 mutex + 直接广播*：代码更短，但"广播时对某个连接写阻塞"会拖慢整个广播，正好撞上规格里"MUST NOT 因某个接收方异常而阻塞其他接收方"。
- *actor 库*：引入依赖解决一个用 30 行 channel 就能解决的问题。

**关键细节**：发送队列满时**关闭该连接**而不是丢弃消息。丢消息会让客户端出现序号空洞，破坏"序号连续"的契约；关连接则触发客户端重连并走历史补发，结果是一致的。

### 4. 存储：单写者协程 + 快照原子替换

**选择**：`Storage` 接口按领域切分方法（用户、频道、成员、消息），JSON 实现内部用一个写协程串行化所有写操作；提交时写临时文件、`fsync`、再 `os.Rename` 覆盖。

**理由**：JSON 文件最怕两件事——并发写互相覆盖，以及写到一半崩溃留下半截文件。串行化 + rename 同时解决两者：`rename` 在同分区上是原子的，读方要么看到旧版本要么看到新版本。

**替代方案**：
- *每次写都加文件锁*：跨平台语义差异大（Windows 的 `LockFileEx` 与 POSIX 的 `flock` 行为不同），且锁粒度难控制。
- *追加日志（append-only log）+ 定期压缩*：写性能更好、崩溃恢复更细，但实现复杂度显著上升，且初期数据量根本用不上。留作后续演进路径。
- *直接用 SQLite*：长期更正确，但用户当前明确选择 JSON 文件；`Storage` 接口已经把切换成本压到只写一个新实现。

**内存策略**：启动时全量载入内存，读操作零 IO；写操作更新内存后异步落盘。这意味着进程内存随历史消息线性增长——对本项目规模可接受，且在接口层保留了"读走存储、只缓存热数据"的演进空间。

**分片**：消息按会话分文件（`messages/<conversation-id>.json`），避免单个巨型文件导致每次写都要序列化全部历史。用户与频道元数据各自独立小文件。

### 5. 密码用 Argon2id，令牌用随机 opaque 字符串

**选择**：`golang.org/x/crypto/argon2`，参数存于每条记录的编码串中（PHC 格式）；令牌是 32 字节 CSPRNG 随机值的 base64url 编码，服务端保存哈希后的令牌以便按值查找同时不落明文。

**理由**：Argon2id 是当前密码哈希的稳妥默认，抗 GPU 与 side-channel；PHC 格式把参数嵌在字符串里，天然支持"参数升级后登录时重哈希"这条规格。opaque token 相比 JWT 的好处是**可即时吊销**——规格要求登出后立刻失效，JWT 做不到（除非维护黑名单，那还不如直接用 opaque）。

**替代方案**：
- *bcrypt*：成熟但内存硬化弱于 Argon2id，且 72 字节截断对长密码不友好。
- *JWT*：无状态、便于多机，但吊销困难，且本项目没有多机需求。

### 6. 渲染：每帧全量重绘 + 脏区优化留给后续

**选择**：视图实现 `Render(screen)` 每帧清屏重绘，`tcell` 内部做 cell diff 后只发送变化的字节。帧率由事件驱动（输入/消息到达）而非固定 tick，仅动画存在时才以固定间隔刷新。

**理由**：`claude_manager` 已验证这条路径在 Windows Terminal 上足够流畅。全量重绘让布局代码可以写成"给定状态 → 输出画面"的纯函数，这是可测试性的关键——布局测试不需要模拟终端，只需断言输出的 cell 网格。`tcell` 的 diff 已经消除了全量重绘的主要成本。

**替代方案**：
- *自己维护脏区*：在 60 列的聊天界面里，收益小于它带来的错误（漏刷、残影）。

### 7. 设计系统以"令牌 + 网格"两层落地，不用组件框架

**选择**：`pkg/tui/theme` 持有语义令牌（含能力降级后的实际颜色），`pkg/tui/layout` 提供网格常量与折行/截断等纯函数；视图直接用 `tcell` 的 `SetContent` 组合。

**理由**：规格里"高级感"的可验证部分是**一致性**——所有缩进落在同一列、所有颜色来自同一张表、选中态在所有列表里表现相同。这些都能由令牌与网格强制，而不需要一层运行时组件树。反过来，组件框架会把 `tcell` 的即时模式变成保留模式，多一层状态同步，对这个界面是净负担。

**关键实现点**：
- 所有宽度计算走 `go-runewidth` 的 `StringWidth`，绝不使用 `len()`。CJK 与 emoji 是终端布局错误的第一来源。
- 折行函数是纯函数 `Wrap(text, width) []string`，按 rune 逐个累加显示宽度，遇到宽度溢出即断行，并保证不拆散组合字符。
- 降级在 `theme` 初始化时一次性决定（检测 `TERM`、`COLORTERM` 与 `tcell` 的颜色容量），视图代码不感知终端差异。

### 8. 客户端状态：单一 `AppState` + 事件归约

**选择**：客户端维护一个 `AppState`（当前用户、会话列表、各会话消息缓存、输入草稿、连接状态、UI 焦点），所有输入事件与网络事件被归约为对它的变更，然后触发重绘。

**理由**：三栏布局 + 对话框 + 重连状态机组合后，状态分散是 bug 的主要来源。归约式更新让"某个事件后界面应该是什么样"可以被单元测试直接断言（构造状态 → 应用事件 → 断言状态），而不需要跑一个真实终端。

**替代方案**：
- *每个视图持有自己的状态*：简单，但重连补偿、未读计数这类跨视图行为会立刻变成状态同步问题。

### 9. 重连：指数退避 + 补偿拉取

**选择**：断开后按 `1s, 2s, 4s, ...` 退避重连（上限固定），重连成功后重新认证，然后对每个已打开的会话拉取"最后已知序号之后"的消息。

**理由**：规格要求"补拉断开期间的消息"且"新消息不打断阅读"。用序号而非时间做补偿锚点，是因为序号在服务端是唯一且连续的，而时间戳有精度与时区问题。认证失败时直接退出重连循环进入登录界面，避免拿着过期令牌无限重试。

## Risks / Trade-offs

- **JSON 文件在消息量增长后写放大严重** → 按会话分片消息文件，单文件只承载一个会话的历史；`Storage` 接口保证换 SQLite 时业务层零改动。上线前用十万条消息做一次写入压测量化拐点。
- **全量重绘 + 大历史缓冲可能在高频消息下掉帧** → 客户端消息缓存按会话限长（内存中保留最近 N 条，更早的依赖翻页重取）；渲染按事件合并，同一帧内的多条到达只重绘一次。
- **单进程 Hub 是单点** → 明确列为 Non-Goal；用健康检查 + 进程守护保证快速重启，关停前确认已写入的消息不丢。
- **终端能力差异导致"高级感"在部分终端失效** → 设计系统把降级路径写进规格与实现，CI 中用宽度单测覆盖 CJK/emoji；人工在 Windows Terminal、iTerm2、VSCode 三个终端上做验收。
- **令牌存在客户端配置文件中** → 配置文件权限收紧（POSIX 0600），Windows 下存放于用户目录而非项目目录；文档中明确这是"可被本机其他进程读取"的既定权衡，与浏览器 cookie 同类。
- **限流阈值选错会误伤正常用户** → 阈值全部可配置，先按"单连接 20 req/s、单来源登录失败 5 次退避"的保守值上线，观察日志后调整；错误响应中带 `retry_after`，客户端据此提示而不是硬编码等待。

## Migration Plan

新工程，无迁移负担。落地顺序按依赖关系推进：

1. 仓库骨架 + `go.mod` + Makefile + `openspec/project.md`（建立规范上下文）。
2. `pkg/protocol`（两端共同依赖，先定型）。
3. `pkg/storage` 接口 + JSON 实现（含原子写与并发测试）。
4. `pkg/server`（Hub、认证、限流、路由、TLS、健康检查、优雅关停）。
5. `pkg/tui/theme` + `layout`（设计系统，先用一个静态样张页面验证观感）。
6. `pkg/client`（连接状态机、重连、状态归约）。
7. `cmd/link-chat` 界面与交互（会话列表 → 消息流 → 输入区 → 登录与设置）。
8. 端到端联调 + 三终端验收。

**回滚策略**：每个阶段独立可运行——协议与存储有测试即可验证，服务端可在无客户端时用手写 WebSocket 脚本测试，客户端可对空服务端展示空状态。任一阶段出问题不影响已合并部分。

## Open Questions

- 未读计数是否需要跨设备同步（当前按设备各自计数）。这不改变协议结构，只需在会话元数据里加字段，可后续决定。
- 消息保留策略（是否要按时间或条数自动裁剪历史）。JSON 文件下这会影响文件组织方式，但 `Storage` 接口已预留删除能力。
- 是否需要"频道创建者转让"与管理员角色。当前只有创建者权限，规格未覆盖角色体系。
